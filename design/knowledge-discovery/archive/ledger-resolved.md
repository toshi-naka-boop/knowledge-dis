## D-0: レーン1回答方式（決定3 vs 決定4の矛盾）

**指摘**: spec.md 決定3「人間が書いた、または機械が下書きし本人が承認したテキストのみ流通可。未承認の機械生成テキストは型付きフィールドのみ」と、レーン1の動作「受信側エージェントが承認済みナレッジの範囲のみで回答/リンク返却」が、実装レベルでは矛盾し得る。受信側エージェントが質問に対しその場で回答文を**生成**すると、生成物自体は本人が見たことのない未レビューの機械生成テキストであり、決定3に反する。幻覚や、承認済み文書にない暗黙の情報（人間関係の機微・裏ハック的な抜け道）が本人名義で流れるリスクがある。

**破綻シナリオ**（チャットUI検討時にFable 5が提示した具体例）:
質問「経費精算の締めっていつ？」に対し、田中さんのエージェントが「締めは毎月25日です。ちなみに遅れても佐藤部長に直接言えば通ります」と回答した場合、前半は承認済み文書の事実だが、後半はエージェントが混入させた（幻覚 or 学習データ由来の）内容で、田中さん本人はこの文を見たことがない。

**選択肢**:
- 案a: レーン1は「引用＋リンク＋型付きメタデータ」のみ返す。エージェントは承認済みテキストから該当箇所を選ぶだけで、文章を生成しない
- 案b: 生成要約を許可するが「AI生成・本人未確認」フラグを型で必須化し、生成コンテキストを承認済み文書のみに物理制限するガードを併設する

**解決**: design.md §1 で案aを採用。
理由:
1. 決定3と完全に一致する（生成物ゼロなので矛盾が構造的に発生しない）
2. 実装コストが低く、2週間の制約に適合
3. レーン1の価値は文章の巧さでなく正しい情報源への到達であり、引用形式でも説得力は落ちない
4. Fortifiedトラックの審査基準「Architectural Discipline」に対し「エージェントは代弁者ではなく配達人」という設計原則を明確に示せる

決定日: 2026-08-18（design.md v1 起草時点）

## C-1: 396体の非対話プロフィールの扱い（レーン1状態機械の未完成）

**指摘元**: 批評ラウンド1（design-critic, claude-opus-5[1m]）、reviews/round-1.md
**種別**: 設計 / 深刻度: high

**指摘**: 「396体を上位k体の選定対象に含めるが応答は返さない」という設計は、レーン1完結条件・レーン2遷移条件・`no_match` の生成主体・無応答時のタイムアウトのすべてを未定義のまま放置しており、デモの幸福経路が確率的に成立しない。加えて、未レビュー生成物（396体のプロフィール）が選定結果として質問者UI・監査ダッシュボードに表示される経路が残り、決定3に抵触する。詳細な破綻シナリオは reviews/round-1.md 参照。

**選択肢**: critic は「案A: 全件検索+配送のみフィルタ」「案B: 合成データのトピック重複回避」を提示し、決定13の解釈に関わる価値判断のためユーザー確認を推奨した。

**解決**: ユーザーが案Aを選択。design.md v2 §1手順2-3・§3・§5に反映:
- ベクトル類似度検索は400件全体に対して実行し、上位20件を候補として監査ログに記録（隠蔽しない）
- 配送対象は `implemented=true` でコード側フィルタし、上位k体を確定
- `no_match`/無応答/配送対象なし(k=0)を単一のT秒集約タイムアウト機構に統一し、状態機械を閉じた

決定日: 2026-08-18（design.md v2、ユーザー選択反映）

## C-2: private絞り込みの実施層未定義（プロンプトインジェクション経路）

**種別**: 設計 / 深刻度: high

**指摘**: `visibility="public"` への絞り込みをどの層で行うかが未定義。プロンプト依存の実装だと private 本文がプロンプトインジェクションで citation として流出し、スキーマレジストリの型検証はこれを検出できない。「2段防御」がどちらの段も機能しない。詳細な破綻シナリオ・攻撃例は reviews/round-1.md 参照。

3. §9検証ゴールに異常系（インジェクション文字列を投げてもprivate本文が出現しない）を追加

## C-3: 監査ログのアクセス制御未設計（辞退不可視の自壊リスク）

**指摘元**: 批評ラウンド1（design-critic, claude-opus-5[1m]）、reviews/round-1.md
**種別**: 設計 / 深刻度: high

**指摘**: 監査ダッシュボードが「神視点」であるという位置づけの宣言のみで、データアクセス制御による隔離がない。クライアントがFirestoreを直接購読する構成だと、質問者側からも `declined` 行が読める。加えてデモ動画の監査画面シーンに `declined` 行が実名付きで映り、「辞退不可視」という中核主張が動画自体で自壊するリスクがある。詳細は reviews/round-1.md 参照。

**解決**: design.md v2 §3・§7・§8に反映:
1. `messages`・`profiles` を Firestore Security Rules で `allow read, write: if false` にし、クライアント直接アクセスを全面禁止
2. Cloud Run サーバーAPI経由のロール別射影を導入: 質問者ロールは `granted`/`declined` の別を返さない。監査者ロールは既定で結果を伏せた二段表示にする
3. §8に認証情報管理（サービスアカウント最小権限・Secret Manager・Security Rules）を明記し、Fortified審査軸「Architectural Discipline」への対応を設計書に残した

決定日: 2026-08-18（design.md v2）

## C-6: サーバーAPIのロール判定・本人識別の認証手段未定義

## C-7: T秒定時応答の性質混同（レーン1レイテンシ吸収とレーン2秘匿の同一機構流用）

**指摘元**: 批評ラウンド2（design-critic, claude-opus-5[1m]）、reviews/round-2.md
**種別**: 設計 / 深刻度: high

**指摘**: レーン1のTは機械のレイテンシ吸収、レーン2のTは人間の応答時間を隠す秘匿パラメータで、必要な値が桁で違うにも関わらず同一機構・同一既定値(10秒)を流用していた。Cloud Run min-instances=0のコールドスタートでレーン1が10秒を超過するとレーン2に誤遷移し、人間への通知が発生してしまう。逆にレーン2のTを人間の応答時間として現実的な値に伸ばすと、同期ブロックの実装が破綻する。詳細は reviews/round-2.md 参照。

**解決**: design.md v3 §1・§5に反映:
1. `T_lane1`（レーン1、同期ブロック、暫定20秒・実装初日に実測して確定）と `T_lane2`（レーン2、非同期deadlineポーリング、暫定5分）を分離
2. `T_lane1`超過後の遅延citationは`intent=late_citation`として監査ログにのみ記録し、質問者UIには出さない
3. `T_lane2`はFirestoreにdeadlineを記録し質問者UIがポーリングする非同期方式に変更。deadline経過後の`granted`は`withdrawn`扱いにする
4. §1手順7/8の「1件のみ提示」と「複数並べて表示」の矛盾も解消し、1件のみ提示に統一

決定日: 2026-08-18（design.md v3）

## C-14: MIN_QUOTE_LENGTHが短いbody項目からの引用を構造的に拒否する誤爆

**指摘元**: 批評ラウンド3（design-critic, claude-opus-5[1m]）、reviews/round-3.md
**種別**: 設計 / 深刻度: mid

**指摘**: v3で追加した`MIN_QUOTE_LENGTH=20文字`が、`body`自体が20字未満の短い項目（例:「対応可能言語: 英語・中国語」）からの引用を常に`reject_provenance`で拒否してしまい、正常系デモ中に赤行を誤爆させる。`MAX_QUOTE_LENGTH`も未定数化だった。詳細はreviews/round-3.md参照。

**解決**: design.md v4 §1手順7に反映。判定を`len(normalize(quote)) >= min(MIN_QUOTE_LENGTH, len(normalize(body)))`に変更（body全体を引く場合は最小長を免除）。`MAX_QUOTE_LENGTH`（暫定300文字）を定数化し`MAX >= MIN`を不変条件として明記。検証ゴールの境界値テストにbody短文ケースを追加。
