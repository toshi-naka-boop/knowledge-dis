## Round 5 — 2026-08-18 — 工程: 批評（design.md v6 / spec.md v4 前提での2巡目）

前提確認: ledger.md の「前提変更の記録」と新前提の解決済み索引（C-16〜C-20）に従い、廃止済み機構（来歴検証・reject_visibility・定時応答・ロール別射影・セッションロール認証・辞退不可視）の復活は提案していない。C-16の2トラック分離、C-19の監査主張範囲（事実は記録・内容は非表示）、C-20の工数判断（レビューUI最小化・doc添付採用・GEAP実採用なし）は既決として受け入れ、蒸し返していない。本ラウンドの指摘は**v6で新たに導入された機構が生んだ穴**（C-21/C-23/C-24/C-25）と、**spec側が未追随のまま残った記述**（C-22）に限定する。

### 指摘

- [C-21] 種別: 設計 / 深刻度: high
  - 指摘: C-18で導入した「`cited_item_keys` × `visibility` による機械的マスク」は `connect_ask` 系にしか適用されず、C-16で新設した**足切り経路（`no_connection`）が同じ検査を通らない**。その結果、private項目を引用した `reason_text` が無検査・平文で監査ダッシュボードに表示される経路が新設された。C-18が塞いだ穴が、C-16の直しによって裏口から復活している。
  - 破綻シナリオ:
    - §2の2段目は候補エージェント自身が**自分のprivate項目を含む全文**を見て `{connection: {reason_text, score, cited_item_keys}}` を返す。候補Dのprivate項目が「A社との統合案件（NDA）のPMO」で、質問が「製造業の商習慣の肌感」の場合、`reason_text` に「A社統合案件のPMOで製造業クライアントに間接的に接している」、`cited_item_keys=["nda_a_project"]`、`score=0.4` が返る。0.4 < `CONNECTION_THRESHOLD`(0.5) なので**足切り**され、`intent=no_connection` として記録される。§3の機械的振り分けは「`connect_ask_private` に確定する」ルールなので `no_connection` では発火せず、§3の `audit_payload` も「`connect_ask_private` のみpayloadと異なる」と明記されているためマスクが掛からない。§7は「`no_connection` の行は理由付きで通常色表示」と規定しているので、NDA案件名がそのまま監査画面に並ぶ。
    - しかも §2 と §11-1 は「落選候補を1件デモで見せる」ことを**最重要ゴール（§10-2）として台本に組み込んでいる**。その1行が本番一発撮りの映像に映る確率は、round-4 C-18 で懸念したケースより構造的に高い（落選は必ず1件表示すると決めているため）。
    - 副次: §3の監査表示規則は「`audit_payload` があればそちらを表示する」= **fail-open**。intent を追加するたび付け忘れが平文表示になる方向に倒れる。`no_connection` はその1例目である。
    - 副次: 2段目の出力スキーマが `{connection: {...} | null}` のみのため、`connection: null` のとき `no_connection.payload.reason_text` の**出所が存在しない**（§3は `no_connection: {reason_text}` を要求している）。実装時に必ず詰まり、その場しのぎで「nullの理由も自由文で返させる」拡張をすると、それがprivate参照済みの自由文となり本指摘の穴をさらに広げる。
  - 提案（いずれも設計書への追記のみ、実装コストはほぼゼロ）:
    - 機械的振り分けのルールを intent 別ではなく**メッセージ横断の1ルール**に書き換える: 「`cited_item_keys` に `visibility=="private"` の項目が1つでも含まれる**すべての**メッセージについて、送信層が `audit_payload` を生成する」。`connect_ask`→`connect_ask_private` への intent 確定はその副次規則とする。
    - `no_connection` の payload を `{reason_text, cited_item_keys, score}` に揃える（2段目の出力スキーマを `{connection: {...} | null, no_connection_reason: string, cited_item_keys: string[]}` に統一し、null時も cited_item_keys を返させる）。
    - 監査表示を fail-open から**fail-closed**へ: 「`audit_payload` が null のときのみ `payload` を表示してよい payload_type をスキーマレジストリ側にホワイトリストで持つ」か、最小案として「`no_connection` の監査表示は `reason_text` を出さず `score` と `cited_item_keys` の件数のみ」にする。後者ならデモの「落選を理由付きで見せる」訴求は、public項目のみを引用した候補（経理担当など）を台本で選べば維持できる。

- [C-22] 種別: 前提 / 深刻度: mid
  - 指摘: design v6 が確定させた方針に対し、**spec.md v4 側の記述が3箇所未追随**で残っている。現在「唯一の真実」が2つに割れている状態で、write-up・自己チェック・実装終盤の判断がどちらを見るかで結果が変わる。
  - 破綻シナリオ:
    - (a) **spec FR12**: 「非公開項目を狙う不正なクエリの拒否は同画面に赤色表示される」。しかし ledger C-11 で「reject_visibility は作らない／NDA情報を狙う質問には人間の判断に委ねる」がユーザー決定として確定しており、design v6 §7 の赤表示は `rejected=true`（未登録 payload 型）のみ。8/27頃に FR チェックリストを回した実装者が「FR12未達」と判断して、凍結2日前に廃止済みの悪性クエリ検知を作り始める余地がある。逆に何もしなければ、write-up 提出物と spec が食い違ったまま残る。spec §構造図の `Bad[非公開のNDA業務情報を直接狙う不正クエリ]` ノードも同じく未追随。
    - (b) **spec 完了条件1**: 「約400名分のプロフィール索引から上位k体が選定され」。design v6 は2トラック分離により、配送用ランキングは `agents` レジストリ登録済み4体へのプリフィルタ後に決まる（400件からの選定ではない）。C-16の「スケール表示として誠実に明示する」判断は正しいが、その判断が spec の完了条件文面に反映されていないため、完了条件をそのまま読むと未達に見える。
    - (c) **spec 完了条件4 / FR8**: 「非公開項目の内容が依頼者・他エージェント・**監査画面**のいずれにも表示されない」。design §4-4 は「事実は記録・内容は非表示」で両立すると主張しており内容としては整合するが、spec 文面が「表示されない」のままだと、C-19の主張範囲の精緻化が仕様に定着していない。write-up でこの一文を英語化するときに主張がぶれる。
  - 提案: spec.md を v5 に上げ、(a) FR12 と構造図の Bad ノードから悪性クエリ検知を削除（「未登録 payload 型の拒否」に置換）、(b) 完了条件1を「配送用ランキング（レジストリ登録済み）と画面用ファネル（400件のスケール表示）の2トラックが確認できる」に改訂、(c) 完了条件4に「監査画面には打診が行われた事実のみが記録され、内容はマスクされる」を追記。design側の再起草は不要で、spec の文言修正のみ。

- [C-23] 種別: 設計 / 深刻度: mid
  - 指摘: §10-2 を「最重要ゴール」と自認しながら、その成否が **LLMの自己申告 `score`（未較正）とプロンプト指示だけ**という単一の不安定な信号に依存している。C-18で「判定主体をLLMから型システムに移す」と宣言した直後に、デモの最重要論点の判定をLLMの自己申告に戻している。フォールバックが設計書にない。
  - 破綻シナリオ: LLMの自己申告confidenceは較正されておらず、「関連度を0〜1で出せ」と指示すると無関係な入力に対しても0.6〜0.85に集中する既知の傾向がある。8/26頃にシードデータで較正しようとすると、4体×質問3種＝12サンプルの `score` がほぼ全て0.7超で分布し、`CONNECTION_THRESHOLD` を0.8に上げても「落ちる候補」と「通る候補」の境界が試行ごとに反転する（同一入力でも温度によりブレる）。結果、§11-1 の台本「配送3件・落選1件」が収録のたびに変わり、再現しない画面を3分動画に組み込めない。凍結（8/29）直前にここで詰まると、逃げ道は「落選シーンを削る」しかなく、round-4総評が「そこだけは削らないこと」と指摘した反証可能性の証拠が丸ごと消える。
  - 提案: 落選判定を**決定的な信号と併用**すると1行で決めておく。(a) 配送用ランキングで既に計算しているベクトル類似度（決定的・再現可能）の下限を第1関門にし、LLMの `connection: null` を第2関門にする（AND ではなく OR で落とす）。(b) 台本用に「確実に落ちる1体」をシード設計時に作り込む（例: 経理担当のプロフィールに、質問ドメインと語彙が一切重ならないよう意図的に設計する）。(b) だけでもデモは守れる。§13の「`CONNECTION_THRESHOLD` は暫定値、シードで較正」に、較正が収束しなかった場合のフォールバックを1文添えるだけでよい。

- [C-24] 種別: 実装 / 深刻度: mid
  - 指摘: C-20で採用した `doc` 添付（GCS事前配置＋署名URL）に必要な**IAM権限が §8 の権限設計に入っていない**。§8 は「Cloud RunサービスアカウントはFirestoreへの最小権限」としか書いておらず、GCSも署名権限も言及がない。Cloud Run のデフォルト認証情報は秘密鍵を持たないため、素直に書いた署名URL発行コードは実行時に失敗する。
  - 破綻シナリオ: Cloud Run 上で `blob.generate_signed_url(version="v4", expiration=...)` を呼ぶと、メタデータサーバ由来の認証情報には秘密鍵がないため `you need a private key to sign credentials` で落ちる。回避には (1) SA に自分自身への `roles/iam.serviceAccountTokenCreator` を付与し、(2) `service_account_email` と `access_token` を明示的に渡して IAM SignBlob 経由で署名する、という2段の設定が要る。ローカル（SA鍵ファイルあり）では動くのにデプロイ後だけ落ちる典型パターンで、原因に辿り着くまで1名・業務外時間だと半日〜1晩溶ける。辞退＋添付シーンは §11-1 の幸福経路に組み込まれた必須カットなので、ここが動かないとデモ台本が丸ごと止まる。
  - 提案: デモの脅威モデル（社内・収録後即停止）では署名URLである必然性が薄い。(a) GCSを使わず、`doc` の実体を Cloud Run 自身の静的配信（`/attachments/<id>` として同一サービスから返す）にすれば、権限設計・署名・期限がまとめて消え、既にある単一APIキー保護の内側に収まる。(b) GCSを使うなら §8 に `storage.objectViewer` と `iam.serviceAccountTokenCreator`（自己）を明記し、実装最初のタスク（§13のベクトルインデックス確認と同枠）に「デプロイ環境での署名URL発行の疎通確認」を追加する。どちらでもよいが、8/19に決めてしまうこと。

- [C-25] 種別: 設計 / 深刻度: low
  - 指摘: `agents` レジストリの `supported_intents` がどこからも参照されないデッドフィールドになっている（過剰実装の芽）。§3は「登録済み・activeなエージェントにのみ配送する」としか書いておらず、判定に使うのは存在と `active` のみ。4体とも同じ値を持つので実質的な統制効果はゼロ。
  - 破綻シナリオ: リポジトリを読んだ審査員が、write-up・アーキ図で「誰が居るか（agent discovery）」の実体として提示されたレジストリを開くと、実際に効いているのは boolean 1個（`active`）で、round-4 C-20 が指摘した `implemented: boolean` の状態から**フィールドが増えただけ**であることが分かる。Architectural Discipline 30% において「レジストリ化した」という主張が飾りと読まれる。逆に、使わないフィールドを残すこと自体が Simplicity First への違反でもある。
  - 提案: どちらかに倒す。(a) `supported_intents` を削り、レジストリは `active` による配送ゲートに絞る（正直で最小）。(b) 送信層に「宛先エージェントの `supported_intents` に含まれない intent は `reject_unsupported_intent` で拒否」を追加する（既存の `reject_unregistered_type` の隣に数行、監査画面の赤表示も既存機構を再利用）。(b) を採ると、レジストリが実際に流量を止める機構になり、「誰が居るか＋何を流せるか＋何が流れたか」の3点セットが**主張ではなく実装として**成立する。デモ尺の余裕（§11-3の「尺が余れば」枠）とも噛み合う。

### 総評（賛成側の根拠、最も危うい前提、GEAPリスクの補い方）

**賛成側の根拠。** v6 の3つの直しは、いずれも「安全機構を足す」ではなく「判定の主体を移す／主張を実態に合わせる」方向で解かれており、round-4 が指摘した構造問題に正面から答えている。特に (1) C-17由来の独立推論（データ境界＝プロセス境界）は、Starmind型との差異を実装構造として示せる本設計唯一の技術的セールスポイントであり、ADKマルチエージェント構成である必然性をここだけが担保している。(2) C-16由来の「配送に寄与しない演出であることを隠さずナレーションで言い切る」判断は、デモ齟齬という最も痛い失点を、誠実さをスケール訴求に転換することで消している。(3) C-19由来の「事実は記録・内容は非表示／存在秘匿は依頼者UIに限る」という主張範囲の切り分けは、監査要件と情報主権の両立点を正確に射抜いており、write-up の英文一文にそのまま使える強度がある。

**最も危うい前提。** v6 は「判定をLLMから型システムに移した」という物語を採用したが、実際に移せたのは public/private の振り分け1点だけで、**落選判定（C-23）と落選理由の安全性（C-21）はLLM出力に置かれたまま**である。この非対称に気づかないまま write-up で「エージェントの自己申告に依存しない統制」を主張すると、リポジトリを読まれた瞬間に主張と実装の距離が露呈する。C-21 と C-23 は本質的に同じ根から出ており、どちらも「LLMの出力を、決定的な信号（`visibility`／ベクトル類似度）で挟む」という同一の処方で消える。

**GEAP実採用ゼロのリスク（§8）の補い方の評価。** 「自前実装の設計意図をwrite-upで明記して補う」という方針は方向としては正しいが、現状の書き方では**不十分**と判断する。「使わなかった理由の説明」は審査軸に対して防御的な語りにしかならず、Architectural Discipline 30% を積極的に取りにいけない。補強するなら、説明ではなく**対応関係を構造で示す**こと: (1) `agents` レジストリのフィールド名を GEAP Agent Registry の agent card 相当（agent_id / capabilities / endpoint）に意図的に寄せ、「同一の責務を最小実装で満たしており、レジストリの実体を差し替えるだけで移行できる」とアーキ図に1対1対応表として載せる。(2) 送信層のスキーマレジストリ検証を Model Armor の、`messages` コレクションを Agent Observability の、それぞれ責務対応物として同じ表に並べる。これで「推奨技術を使っていない」ではなく「推奨技術が担う3責務を全て最小実装で実現し、置換点を明示した」という主張になる。C-25(b) を採ると、この表の「何を流せるか」の欄が実装で裏付けられ、表全体の説得力が変わる。write-up 執筆（8/29以降）ではなく、アーキ図の構成を決める時点で決めておくべき事項。

**承認CPへの判断。** high 1件（C-21）あり。ただし C-21 の修正は**設計書 §3/§7 への追記のみで、実装量は増えない**（振り分けルールを intent 別からメッセージ横断に書き換え、`no_connection` の payload に2フィールド追加、監査表示を fail-closed に）。C-21 を反映すれば、設計として破綻する論点は残らない。C-22〜C-25 はいずれも「今決めれば0コスト・後で気づくと時間を溶かす」類で、承認CPを止める性質のものではない（C-22 は spec 側の文言修正としてユーザー判断が要る）。
