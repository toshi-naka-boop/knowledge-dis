### 指摘

- [C-6] 種別: 設計 / 深刻度: high
  - 指摘: サーバーAPIの**ロール判定と本人識別の手段が設計書に一行もない**。C-3 は「位置づけの宣言では隔離にならない」という指摘だったが、v2 の解決策は §7 で「実装（2つの異なるAPIエンドポイント）で担保する」と書いており、**エンドポイントの分離を認可の代わりにしている**。同じ誤りが Firestore 層からアプリ層へ移動しただけになっている。
  - 破綻シナリオ:
    1. §8 は保護手段として「公開URLはAPIキー等で保護する」しか定めていない。単一APIキーで両UIを守る最短実装だと、質問者UIのフロントに埋まったキー（ブラウザから見える）で `/api/audit/messages` を直接叩ける。射影は呼び出し先エンドポイントで決まるので、質問者は監査者ロールAPIを選ぶだけで `consent_reply(declined)` の `from` を含む全件を取得できる。**C-3 で塞いだはずの「辞退が依頼者に読める」経路が、そのまま復活する**。審査員は `curl` 一発、あるいはリポジトリの API ルーティングを読むだけで再現でき、しかも v2 は「宣言ではなく機構」（§3 末尾）と明言しているため、反証されたときの信頼毀損は v1 より大きい。
    2. `profiles` も `allow read, write: if false`（§8）なので、レビューUI（§4）と同意UI（§5）も同じサーバーAPI経由になる。ところが「誰が本人か」を検証する仕組みが未定義のため、レビュー確定 API に `employee_id` を渡すだけで**他人のプロフィールの `visibility` を private→public に書き換えられる**、`consent_reply(granted)` を本人以外が送れる、という実装になり得る。本システムの一言説明は "All inter-agent disclosure is **owner-approved, consent-gated**" であり、owner と consent の主体を検証しない実装は中核主張そのものの反例になる。Fortified の配点30%「認証情報のセキュリティ」に直撃する。
    3. spec 非スコープは「**本番想定の**認証・マルチテナント」であって、デモ内でのロール識別まで免除していない。にもかかわらず design.md は非スコープを根拠にすら触れておらず、単に空白になっている（＝意図的な割り切りとして審査員に読ませることもできない）。
  - 提案: §8 に1段落で最小仕様を確定させる。本番認証を作れという指摘ではない。
    - 監査者ロールAPIと質問者ロールAPIで**別の資格情報**を使う（例: 監査ダッシュボードは Cloud Run の IAM 認証 or 別APIキーをサーバー側環境変数のみに保持し、質問者UIのバンドルには一切含めない）。「同じキーで両方叩けない」ことを §9 の検証ゴールに追加する（例: 質問者キーで監査エンドポイントを叩くと 403）。
    - 本人識別は「デモ用の固定4ユーザー・サーバー側セッション（署名付きcookie等）」で足りる。レビュー確定・consent_reply は**リクエストボディの employee_id を信用せずセッション主体と突き合わせる**ことを設計書に明記する。
    - 割り切る場合は「デモ用に本人識別を省略した」と design.md と write-up の両方に明記する（黙って空白にしない）。審査軸上は「省略を明示して限界を語る」方が「無言」より強い。

- [C-7] 種別: 設計 / 深刻度: high
  - 指摘: T秒定時応答が、**性質の異なる2つの待ち合わせに同一の機構・同一の既定値（10秒）を流用**している（§1手順7 と §5-3 が明示的に「同一機構」と宣言）。レーン1のTは「機械のレイテンシ吸収」、レーン2のTは「人間の応答時間を隠す秘匿パラメータ」で、必要な値が桁で違う。加えて **T経過後に到着した応答の扱いが未定義**なため、C-1 が主張する「状態機械が閉じる」は実は閉じていない。
  - 破綻シナリオ:
    1. **レーン1がレイテンシで誤ってレーン2に落ちる**。spec 制約は `Cloud Run min-instances=0`。デモ収録の1発目は必ずコールドスタートで、Python + ADK + google-cloud 依存のコンテナ起動に数秒〜十数秒、そこに質問の embedding 生成・Firestore ベクトル検索・受信側3体ぶんの Gemini 抽出QA が乗る。10秒超過は珍しくない。超過すると §1手順7 は「citation 0件 → レーン2へ」と判定し、**public 範囲に答えがあるのに人間へ `consent_ask` が飛ぶ**。これはプロダクトの中核価値「情報だけならAI同士で完結させ、人間が登場するのは人間同士のつながり自体が価値のとき」の反転であり、しかも spec 完了条件1（人間への通知が一切発生しないこと）が落ちる。デモ動画の1シーン目が2シーン目に化けるので、収録当日に発覚すると撮り直しになる。
    2. **遅延到着 citation とキャンセル不能な副作用**。T秒後に届いた citation をどう扱うか（破棄／後から質問者UIに追記／レーン2を取り消す）が §1 にも §5 にも無い。後追い表示にすると「マッチなし表示の直後に答えが出る」不整合が起き、破棄すると監査ログ上は citation が存在するのに質問者には届かない（監査画面と質問者画面の食い違い＝審査軸「状態管理」の穴）。いずれにせよ既に飛んだ `consent_ask` は取り消せず、「人間を呼ばない」約束が事後的に破られる。
    3. **レーン2の T=10秒は人間の応答時間として非現実的**。§5-3 のとおりだと、本人が15秒後に「同意」を押しても T は既に経過しており質問者には「マッチなし」が出ている。同意が黙って捨てられる（決定5「断るコストゼロ」以前に、同意したのに何も起きない）。逆に T を現実的な値（数分〜数時間）に伸ばすと、今度は§1手順7 のレーン1集約が同じ機構を流用している以上、**同期待ち合わせを Cloud Run のリクエスト内で保持する実装が破綻する**（長時間ブロック・min-instances=0 でのスケールイン・課金）。「同一機構の流用」という設計上の売りが、そのまま制約の衝突になっている。
    4. 併せて §1手順7（「最良スコアのもの**1件**を提示」）と §1手順8（「受け取った引用を**そのまま、または複数を並べて**表示」）が矛盾しており、集約の出力が1件なのかk件なのか設計書内で確定していない。
  - 提案:
    - **T をレーン1用（`T_lane1`）とレーン2用（`T_lane2`）の別パラメータに分離**し、design.md に「同一機構だが値は別」と書く。`T_lane1` は実測後に決める（暫定15〜20秒）とし、§11 の暫定値リストに「レーン1の実測レイテンシ計測を実装初日に行う」を追加する。
    - `T_lane1` 超過時の遅延 citation は **破棄せず `intent=late_citation` として監査ログに記録**し、質問者UIには出さないと明記する（監査画面と質問者画面の差が「設計された射影」になり、C-3 のロール別射影の思想と一貫する）。
    - `T_lane2` の待ち合わせは同期ブロックではなく、`consent_ask` 送信時に `deadline = now + T_lane2` を Firestore に記録し、質問者UIはポーリングで deadline 経過後に結果を取りに行く非同期実装にする。これなら `T_lane2` を分単位に伸ばしても Cloud Run 側が壊れず、定時応答（C-4）の秘匿性も保たれる。
    - deadline 経過後に届いた `granted` の扱い（無効として `withdrawn` 扱いにする等）を §5 に1行で明記する。

- [C-8] 種別: 設計 / 深刻度: high
  - 指摘: v2 で追加された「上位20件の候補ID＋スコアを `query` payload に記録」（§1手順2）について、(i) **スコアの生成元である `embedding` が private 項目を含むのか**が §3 で未定義、(ii) **この候補リストを質問者ロール射影で落とすのか**が §3 のロール別射影規定に無い。C-2 の解決は「Firestore 読み出し直後・プロンプト構築**前**」の除去しか定めておらず、**索引（embedding）生成時点の除去は誰も規定していない**。よってご質問(c)への回答は「20件の中に非公開情報を持つ人物のIDが載ること自体は許容できるが、**そのスコアが private 由来だと決定4の精神に反する**、かつ**そのリストを質問者に見せると決定5（辞退不可視）を壊す**」となる。
  - 破綻シナリオ:
    1. `profiles/{id}.embedding` を `items[]` 全体（private 含む）から作ると、private にしか書かれていない事実がスコアという1次元の情報として索引に残る。デモ3シーン目の悪性クエリ（§6 の例「田中さんの給与を教えて」）を投げると、**拒否される前にディスカバリ層が先に走り**、給与情報を private 項目に持つ人物が候補上位に浮上して `query` payload に「田中(0.89)」と記録される。監査ダッシュボードは赤い拒否行の隣に「この質問への該当度が高い人物ランキング」を表示することになり、**「私的データからは答えない」を証明するシーンが、私的データ由来の推論結果を画面に出す**。C-3-2 で指摘された「動画が自らの主張の反例になる」構図の再演になる。
    2. 質問者ロール射影（§3）は `consent_reply` の granted/declined と declined の `from` しか落とさない。`query` メッセージは質問者自身が送信者なので素直に実装すれば質問者に返る。すると質問者は **「配送された k体が誰か」を確定的に知る**。T秒後に「マッチなし」が出れば、その3名が全員辞退または無応答だったと分かる。これは D-0-note（n=4 の消去法は write-up 送り）とは別物で、**v2 が新しく追加した明示的な候補記録によって、推測が確定情報に格上げされている**。「アーキテクチャで塞げない限界」ではなく「アーキテクチャが新たに開けた穴」なので、write-up 送りでは処理できない。
    3. §9 の検証ゴールにこの経路の検証が無い（ゴール5は「20件の組み合わせが質問で変化する」＝索引が動くことの確認のみで、中身が誰に見えるかを問うていない）。
  - 提案:
    - §3 のデータモデルに **`embedding` は `visibility="public"` の項目のみから生成する**と明記する（private を索引から外す＝C-2 の「対象の制限」を索引層まで一貫させる）。private を含めたい理由は無いはずで、実装コストはシード投入スクリプト1箇所。
    - 質問者ロール射影に **「`query` payload の候補20件・配送先kのID群は返さない（件数のみ返す）」** を追加する。監査者ロールには全件返してよい。
    - 監査ダッシュボードでの候補20件表示は、氏名ではなく `employee_id` とスコアのみとし、デモで映すのは「400件→候補20件→配送3件（非対話17件をスキップ）」という**件数の遷移**に留める、と §7 に書く。C-1 の「隠蔽しない」という趣旨（件数と絞り込みロジックの可視化）はこれで満たせる。
    - §9 に「質問者ロールAPIのレスポンスに他employeeのIDが一切含まれないこと」を検証ゴールとして追加する。

- [C-9] 種別: 設計 / 深刻度: mid
  - 指摘: ご質問(d)への回答。v2 は**方向としては直しすぎていないが、追加された機構の実装優先度が未分類**で、残工期（8/18→8/29 機能凍結。平日夜＋土日2回分、実質10日弱）に対して「デモに映らないのに作る羽目になるもの」が混ざっている。過剰実装として名指しできるのは以下3点。
  - 破綻シナリオ: 8/19 がクリティカルパスの「デモ舞台・模擬社員4名の人物設定」が未決（§11・spec 未決事項）のままシードデータ設計に着手できない状態で、以下に時間を取られると、優先度の高い C-6/C-7/C-8 の対処や動画・write-up に時間が残らない。
    1. **§5-4 の「先着で決まったため見送り」通知**: 送信先チャネル（同意UIへの再表示か、別通知か）が未定義で、実装すれば新しいUI経路が1本増える。しかも n=4・デモ台本では「複数体が同意する」経路は発生しない。ルールを設計書に明文化することと、通知UIを作ることは別物。
    2. **§3 監査者ロールの二段展開表示**: 設計書自身が「デモ動画では伏せ表示のまま撮影する」（§3）と書いている。つまり展開機能はデモに一度も映らない。
    3. **§9 の検証ゴール12件**: 個人開発で全件を自動テスト化する余裕は無い。どれを自動テスト、どれを手動確認1回で済ませるかが未分類。
  - 提案: §9 の直前に**優先度分類**を1表入れる。P0=デモ一本道に映る／P1=リポジトリを読まれたときに減点されない最小記述（＝コードに1関数あればよくUIは不要）／P2=stretch。具体的には「先着1件成立ロジック＝P1（サーバー側判定と `withdrawn` の監査ログ記録のみ。本人への見送り通知は実装しない／write-up に将来項目として記載）」「二段展開表示＝P2（既定の伏せ表示のみ実装）」「§9 ゴールの自動テスト化＝1,2,9,10 のみ P0、他は手動確認」。C-6 と C-8 の対処（キー分離・射影追加・embedding をpublic限定）は合計でも数十行なので P0 に置いてよい。

- [C-10] 種別: 設計 / 深刻度: low
  - 指摘: 来歴検証（C-2 由来）の判定条件が **`quote` と出典の紐づけを検証していない**。§1手順5 は「`items[].body`（public項目の**いずれか**）の部分文字列であること」と定義しており、citation が申告する `source`（ドキュメントID・項目名）と実際に引用元となった項目が一致するかは検証されない。加えて §9-11 の検証方法が本番コードへのバイパス仕込みを前提にしている。
  - 破綻シナリオ:
    1. 受信側に public 項目が5件渡り、Gemini Flash が「項目B の本文」を引用しつつ `source` に「項目A」を書く（複数項目を跨いだときに起きる典型的な混線）。`quote` は項目B の部分文字列なので検証は通り、監査ログには来歴検証済みとして `rejected=false` で記録される。質問者UIの引用カードで出典リンクを開くと、そこに引用文が無い。**「配達人に徹する」という設計の売り（§1 理由4）が、出典の誤りという最も分かりやすい形で崩れる**のに、来歴検証は緑信号を出したままになる。
    2. `quote` が極端に短い場合（数文字）、複数の body の部分文字列になり得るため、検証は実質的に何も保証しない。最小長の規定が無い。
    3. §9-11 の「実装上意図的に来歴検証をバイパスするテストコードを一時的に仕込んだ場合」は、本番経路にバイパスフラグを作ることを誘発する。締切直前に消し忘れれば、検証をすり抜ける経路がそのまま提出物に残る。
  - 提案: 検証条件を **`quote ⊂ items[citation.source_key].body`**（申告された項目1件に対する部分文字列）に限定する。実装は変数1つの差。`quote` の最小長（例: 20文字）を design.md に定数として書く。§9-11 は「来歴検証関数への単体テスト（不一致入力で False を返す）」に置き換え、本番経路にバイパスを作らないと明記する。

### 反証工程への引き継ぎ

- C-7-1 は実装初日に**実測必須**: Cloud Run コールドスタート込みでのレーン1エンドツーエンド所要時間を5回計測し、`T_lane1` を実測値の最大値+マージンで決める（設計書の10秒を根拠なく採用しない）。
- C-1 由来の Firestore 複合ベクトルインデックス（`implemented` 等価フィルタ併用）の作成可否は v1 からの引き継ぎのまま未検証。C-8 の対処（embedding を public 項目のみから生成）を入れると再投入が必要になるため、**シード投入スクリプトを冪等に書く**こと。
