## Round 4 — 2026-08-18 — 工程: 批評（design.md v5 / spec.md v4 前提での1巡目）

前提確認: ledger.md の「前提変更の記録」に従い、廃止済み機構（来歴検証・reject_visibility・定時応答・ロール別射影・セッションロール認証・辞退不可視）の復活は一切提案していない。C-8（embeddingのpublic限定）の意図的反転も尊重し、embedding側ではなく**2段目推論の実行主体とマスク判定の決定性**という別の層を指摘している。

### 指摘

- [C-16] 種別: 設計 / 深刻度: high
  - 指摘: §2の候補選定2段階は、(1)「候補プール20件の中に implemented=true の4体が入っている」ことを構造的に保証できず、(2) 2段目に「接点なし」の出力路と足切り閾値がないため、常に全候補にもっともらしい理由が付く。核心機構が両端で破綻している。
  - 破綻シナリオ:
    - (1) 400件中4件が implemented。人材紹介会社設定で「製造業の商習慣の肌感」という質問を投げると、396体の合成プロフィール（`current_work` を重点的に作り込むと明記されている＝合成側も濃い）が上位20件を占め、実装済み4体のうち0〜2体しか入らない。§2は「候補プール20件のうち implemented=true の4体について」と全4体の在籍を前提に書かれているが、これは成立しない。プールに1体しか入らなければ k=3 の配送が不能になり、§9-1・§9-8・§10-1（監査画面で「400件→候補20件→配送3件」を見せる）が同時に崩れる。
    - (1') 逆に §12 の「Firestoreベクトル検索（`implemented` フィルタ併用の複合インデックス）」を採るなら、実質4件の中でのランキングになり、画面に出す「20件プール」は選定に何の因果も持たない演出になる。§2本文（400→20→4体を推論）と §12（implementedプリフィルタ）は両立しない2つの設計が同居しており、デモで「400→20→3」を見せた審査員が実装を見ると、20件が配送に寄与していないことがすぐ分かる。Demo & Production Readiness 30% で最も痛い種類の齟齬。
    - (2) 質問と本当に無関係な候補（例: 経理担当）に対しても、Gemini に「背景知識を持っていそうな理由を書け」と指示すれば必ず書く（LLMは要求された生成を拒否しない）。結果、どの質問でも4体全員に🤖付きの説得力ある理由が付き、スコアは順序付けにしか使われないので上位3体が必ず配送される。「探索的マッチング」が「LLMが常にYesと言う」と区別できず、審査員の「誰も知らないことを聞いたらどうなる？」の一問で崩れる。
  - 提案:
    - 選定を2トラックに分離して明文化する。(a) 配送用ランキング = `implemented=true` へのプリフィルタ付きベクトル検索（Firestoreの複合ベクトルインデックスで可能かを実装初日ではなく**設計確定前**に確認）、(b) 画面用ファネル = 400件全体に対する上位20件を「もし全社員にエージェントが居ればここまで探索できる」という**スケール表示**として明示的にラベリングする。演出であることを隠さずナレーションで言い切れば、逆にスケール訴求になる。
    - 2段目の出力に `connection: null` を許す（「意味のある接点は見つからない」）＋ スコア閾値で足切り。デモでは「20件→接点が言語化できた3件→配送」と、**落ちた候補を1件画面に出す**。これが探索的マッチングが機能していることの唯一の反証可能な証拠になり、§9-2（自作の質問と自作のプロフィールで自己採点する循環構造）の弱さも同時に解消する。

- [C-17] 種別: 設計 / 深刻度: high
  - 指摘: §2の2段目推論の**実行主体**が未定義で、文面（「候補プール20件のうち implemented=true の4体について、質問文と各候補のプロフィール全文（本人のエージェントは自分のprivate項目も見てよい）を渡し」）は、ディスカバリ層が4体分のprivate込み全文を1回のGemini呼び出しに渡す実装として最も自然に読める。それは設計書自身の原則2（非公開項目の内容は本人以外の誰にも開示されない／本人のエージェントだけが知っている情報）を実装レベルで破る。
  - 破綻シナリオ: ディスカバリ層が中央でprivate込みプロフィールを集約してプロンプトに詰める実装になると、(a) 全社員の非公開項目を1コンポーネントが常時読める中央データベース型になり、まさにアンチテーゼとして掲げた Starmind/Viva Topics 型の「会社がデータを吸う」構造と実装上は同型になる。write-up で「情報主権」を主張した直後にコードを見た審査員が矛盾を指摘できる状態。(b) Architectural Discipline 30% の評価軸（疎結合性・状態管理）で、4体のエージェントが実質「プロンプトに渡されるデータ」に退化し、ADKマルチエージェント構成である必然性が消える。(c) 実務上も、1プロンプトに4人分の全文を入れると出力が混線し、候補Aの理由に候補Bの経歴が混ざる（LLMの典型的な失敗）。
  - 提案: 2段目は**候補エージェントごとに独立した推論呼び出し**（自分のプロフィールのみをコンテキストに持つ）と設計書に明記する。ディスカバリ層が渡すのは質問文と employee_id だけ、返るのは `{reason_text, score, cited_item_keys}` だけ、という境界を §2 に1文で書く。§12の「4体分の推論を並列化するか直列か」はこの構造を前提にした問いなので、本文と整合させるだけで実装コストは増えない（むしろ4並列で速い）。これはFortifiedトラックにおける最大の技術的セールスポイントにもなる（データ境界がプロセス境界と一致していることを図で示せる）。

- [C-18] 種別: 設計 / 深刻度: high
  - 指摘: `connect_ask` と `connect_ask_private` の振り分けを2段目LLMの判断に委ねる読み方しかできず、監査マスクは `intent=connect_ask_private` の行にしか掛からない（§4-4）。LLMが1回誤ればprivate項目の内容が**非マスクの `connect_ask` 行の `reason_text`** として監査ダッシュボードに表示され、§9-5が破れる。
  - 破綻シナリオ: 候補Dのprivate項目が「A社との統合案件（NDA）のPMO」だとする。2段目が「A社案件でPMOをやっているので統合の実務感を持っている」という reason_text を生成し、intent を `connect_ask`（public）として出力する。マスクルールは intent 一致でしか発火しないので、監査ダッシュボードにNDA案件名がそのまま平文で並ぶ。デモ収録中にこれが1行でも出れば、その場面がそのまま「情報主権を謳ったシステムが非公開情報を垂れ流している証拠映像」になる。LLMの分類は数十回に1回の頻度で外れるので、本番一発撮りのデモでは十分起こりうる。
  - 提案: 振り分けとマスクを**LLMの出力ではなく `visibility` フィールドから決定的に導く**。2段目に `cited_item_keys` を必ず返させ（C-17の提案と同じ出力）、送信層で `cited_item_keys` のいずれかが `visibility=="private"` なら機械的に `intent=connect_ask_private` に確定し、`reason_text` を監査保存時にマスク（本人配信用ペイロードと監査保存用ペイロードを分ける）。追加コストは分岐1つとフィールド1つで、安全機構を増やすのではなく「判定の主体をLLMから型システムに移す」だけ。Fortifiedの審査軸に対しても「エージェントの自己申告に依存しない統制」として説明価値がある。

- [C-19] 種別: 設計 / 深刻度: mid
  - 指摘: 依頼者側の状態モデルと画面が設計書に一度も現れない。その結果、(a) `match_proposal` の payload が §3 の例に無く未定義、(b) 複数同意時（§6-2）と未応答時（§6-3、時限なし）の依頼者画面の見え方が未定義、(c) ロール分離を廃した監査ダッシュボード（§7、単一キーで全員が見られる）を依頼者が開けば `connect_ask_private` 行の存在が見え、§4-2/4-3の「非公開項目がきっかけだったことは伝わらない」と正面から矛盾する。
  - 破綻シナリオ:
    - (b) デモ台本は k=3 で配送し、1体が同意・1体が辞退する。3体目は応答せず、時限も無いので依頼者画面に `pending` が永久に残る。3分動画の最終カットで「未応答1件」が画面隅に映り続け、審査員には「未完成」または「設計されていない状態」に見える。あるいは台本で3体全員を応答させると、辞退2件が並び、幸福経路の印象が薄れる。どちらに転んでも撮り直しになる時間的余裕は8/29凍結時点で無い。
    - (c) デモで依頼者役と監査画面を同一オペレータが操作するので、`connect_ask_private → 田中 → consent granted` の並びが1画面に映る。ナレーションで「依頼者には非公開項目がきっかけだと伝わりません」と言った直後の画面がそれを否定する。
  - 提案:
    - `match_proposal` の payload を §3 に明記し、`reason_text` を**含めない**（依頼者に届くのは相手名・15分MTG提案・同意状態のみ）と1行で決める。これでC-18の漏出経路も1本塞がる。
    - 未応答は「時限を設けない」を維持したまま、依頼者画面の表示語彙だけ決める（`待機中`のまま終了して良い、とデモ台本に書く）。あるいはデモに限り k=2 にして両方応答させる。どちらでも実装コストはゼロ。
    - (c) は「隠す」方向ではなく**主張を実態に合わせる**方向で解決する。監査画面は「非公開項目に基づく打診が行われた事実は記録されるが、内容は誰にも見えない」と言い切る。事実の記録は監査の要件として正当であり、Fortified訴求としてはむしろ強い。§4-2/4-3の「存在自体を伝えない」は依頼者向けUIに限る旨を明記して範囲を絞る。

- [C-20] 種別: 設計 / 深刻度: mid
  - 指摘: 残り10日弱・1名・業務外時間という制約に対して、工数配分が誤っている。デモ台本（§10）に一度も登場しない機能に実装枠を割く一方（プロフィールレビューUI、添付 `type:"doc"`）、Fortifiedトラックの中核訴求に直結する判断（GEAP採用、agent discovery）を「未決」のまま後ろへ倒している。
  - 破綻シナリオ:
    - 実装が必要な画面は最低4面（プロフィールレビュー／依頼者／候補本人／監査）。§12で「レビューUIの形態は未決」のまま8/22頃に着手すると、デモに映らないレビュー画面に週末1日が消え、デモに必ず映る依頼者画面（C-19で未設計）が8/29に間に合わない。FR2/FR3の充足は、下書き生成をバッチスクリプトで実行し、レビューは `visibility` トグルだけの最小画面（または Firestore 直編集＋スクショ1枚）で足り、動画では触れない。
    - 添付 `type:"doc"` は GCS アップロード・署名URL発行・表示の3点セットが必要で、デモの表示例（§5-2）はリンク1本で成立している。`link | text` の2型に絞れば `doc` 由来の実装・権限設計が丸ごと消える。
    - GEAP採用を8/25以降に判断すると、実採用は物理的に不能になり「アーキ図上の将来構成」だけが残る。トラック推奨技術の実採用ゼロは Architectural Discipline 30% の直撃点。加えて、本設計における「エージェントの発見」は `profiles.implemented: boolean` のハードコード1個であり、トラック名が示す agent discovery の実体が無い。
  - 提案:
    - 8/19（舞台設定決定と同日）に、レビューUIは「visibilityトグルのみの1画面・動画非登場」、添付は `link|text` のみ、と確定して §12 から落とす。
    - agent discovery を `implemented` boolean ではなく、**エージェント登録レコード（agent_id / 対応employee_id / 対応intent一覧 / エンドポイント）を持つレジストリ**に置き換える。実装は Firestore の1コレクション（あるいは GEAP Agent Registry の実採用）で済み、既にある `payload_type` スキーマレジストリと並べて「誰が居るか（discovery）＋何を流せるか（統制）＋何が流れたか（監査）」の3点セットとしてアーキ図で語れる。boolean 1個をレコードに昇格させるだけで、トラック適合の説明が構造的に成立する。

### 総評（賛成側の根拠と、最も危うい前提）

本設計は、旧v1〜v4が抱えていた「防御機構が主役になり本体が痩せる」構造を正しく解体できている。特に §4 の非公開項目打診は、削減ではなく**機能の追加**によって情報主権を実体化した設計であり、Fortifiedトラックに対して「制限で守る」ではなく「本人だけが決められる導線を作る」という主張ができる点で、削った防御機構より訴求力が高い。防御機構を減らしたことがトラック適合を弱めるという心配は、C-20の提案（discoveryのレジストリ化）で構造的に回収できる範囲にあると判断する。

最も危うい前提は「探索的マッチングであることが、精度検証をしなくてよい理由になる」という滑りである。誤マッチを許容することと、機構が接点の有無を判別できないこと（C-16の(2)）は別物で、後者は許容ではなく機能不全である。落ちた候補を1件見せるだけでこの区別が付くので、そこだけは削らないことを推奨する。
