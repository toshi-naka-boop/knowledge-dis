### 指摘

- [C-11] 種別: 設計 / 深刻度: high
  - 指摘: **悪性クエリ（`visibility="private"` 項目を直接狙う質問）が「拒否」されず `no_match` になり、§1手順7 の無条件分岐でそのままレーン2へ落ちて人間に `consent_ask` が飛ぶ。** design.md には「private を狙った質問」を検知して赤く止める経路が一行もない。§6 が「3段防御」と呼ぶ3つのうち、質問由来で発火するものが実質ゼロになっている。C-8 の解決（embedding を public 限定）でこの穴はむしろ深くなった——private はスコアにすら影響しなくなったので、悪性クエリはますます「ただの該当なし質問」と区別がつかない。
  - 破綻シナリオ:
    1. **デモ3シーン目が2シーン目の焼き直しに化ける、しかも最悪の絵で。** §6 の例文どおり「田中さんの給与を教えて」を投げる。§1手順4 で private はプロンプト構築前にコード除去済み、embedding も public 限定なので、受信側3体は全員 `no_match` を返す。§1手順7 は「`T_lane1` 経過時点で `citation` が1件もなければ、レーン2へ遷移する」と**無条件**に書いてあるため、システムは田中本人に「会いますか？」を送る。監査画面は赤くならない。**給与を詮索するクエリが、本人への面談依頼に自動変換される**という、"involve humans only when the connection itself is the value" の真逆の絵が3シーン目に出る。撮り直しは収録当日にしか発覚しない。
    2. **spec 完了条件4 が構造的に達成不能。** spec 完了条件4 は「非公開設定項目に触れる質問（悪性クエリ）を投げると、**スキーマレジストリ層で拒否され**、監査ダッシュボードに赤色で表示される」、spec 構造図（L98）も `Bad[非公開項目に触れる悪性クエリ] --> Registry[未登録payload型は送信層で拒否]` と描いている。だが design の機構では、private 直撃質問は正規の `question` 型なのでスキーマレジストリを素通りする。赤行を出せるのは (a) `reject_unregistered_type`＝§6-3 の「不正な payload_type を**注入するテストケース**」（＝質問由来ではなく、動画では「ここでテストスクリプトを流します」になり説得力が落ちる）、(b) `reject_provenance`＝Gemini が捏造引用をした場合（private 本文はコンテキストに無いので捏造は非決定的で、毎テイク赤が出る保証がない）の2つだけ。**spec が要求する「質問を投げる→赤くなる」という因果を再現できる経路が設計内に存在しない。**
    3. round-2 は「spec.md との整合性: FR1〜FR17 と完了条件1〜8 に対する v2 の対応は確認し、欠落は見当たらなかった」と結論しているが、完了条件4 は当時から未充足だった。ここは新根拠ではなく**見落としの訂正**として提起する（ledger の C-1〜C-10 のいずれとも別論点）。
  - 提案: どちらを採るかは**ユーザー確認が必要な設計判断**。実装量はどちらも数十行。
    - **案X（推奨・機構で解く）**: private 除去層（§1手順4 のコード）に「除去した private 項目に対してのみ、LLM を通さず embedding 類似度を計算し、閾値超過なら `intent=reject_visibility`・`rejected=true` で送信を止め、**レーン2へ遷移させない**」を追加する。返すのは拒否の事実のみで、項目キーも本文もスコアも質問者には出さない（監査ログのみ）。C-8 の「private を索引に漏らさない」思想はディスカバリ層の話であり、受信側エージェント内部の自己防衛判定とは両立する。これで「質問を投げる→赤くなる→人間は呼ばれない」がデモで再現でき、spec 完了条件4 の意図（レジストリ層という実装名を除けば）を満たす。
    - **案Y（台本で解く）**: private 直撃質問は `no_match` のままとし、赤表示は型注入と来歴違反の2種に限定する。この場合 **spec 完了条件4 と spec 構造図 L98 の文言をユーザー承認のうえ改訂する**必要があり、かつ §1手順7 に「no_match が全件 private ヒット由来の場合はレーン2へ遷移しない」分岐は依然必要（さもないと破綻シナリオ1が残る）。
    - いずれの案でも §1手順7 の「citation 0件 → 無条件レーン2」は修正が要る。§6 に「どの質問がどの赤行を生むか」の対応表（質問例 → 発火する防御段 → 監査画面の表示）を1表足し、デモ台本を設計書から導出可能にすること。

- [C-12] 種別: 設計 / 深刻度: mid
  - 指摘: **v3 §3 の質問者ロール射影が `payload` レベルにしか及んでおらず、同じドキュメントのトップレベル項目 `intent` と `consent_state` から辞退が丸見えになる。** §3 は「`consent_reply` の `granted`/`declined` の別を返さない」と書くが、§3 のスキーマは intent 列挙に `"consent" | "decline"` を**別値として持ち**、さらに `consent_state: "n/a"|"pending"|"granted"|"declined"` を独立フィールドとして持つ。payload だけマスクして messages ドキュメントを返す最短実装だと、`intent="decline"` / `consent_state="declined"` がそのまま質問者に届く。
  - 破綻シナリオ:
    1. 質問者UIは表示しなくても、質問者ロールAPIキー（フロントに載っている）で `/api/messages` を叩けば JSON に `decline` が入っている。spec FR9「辞退の事実は依頼者側に**一切**表示・通知されない」と完了条件3 が API レベルで落ちる。C-3→C-8 と2度にわたり射影で塞いだ経路が、フィールド1つの列挙漏れで復活する。審査員が `curl` 一発で再現できる形なので、C-6 と同種の信頼毀損になる。
    2. §10-14 の検証ゴールは「配送先k体**以外**のemployee_idや候補20件のIDが一切含まれない」であり、**配送先k体のIDは返してよい**と読める。ところが §3 の射影規定は「候補20件・**配送先kのID群**を返さない」で、両者が矛盾している。§10-14 の緩い方でテストを書くとテストは緑になるが、質問者は配送先3名を確定でき、レーン2で「マッチなし」が出た瞬間にその3名が辞退/無応答だったと確定する（C-8-2 で塞いだはずの経路そのもの）。加えて、レーン1完結時は `citation.from`＝回答者IDを返さないと引用カードが成立しないため、**「レーン1完結時は返す／レーン2遷移時は返さない」という条件分け**がどちらの節にも書かれていない。実装者はここで必ず迷い、緩い方（§10-14）に倒れる。
  - 提案:
    - intent 列挙から `consent` / `decline` を削り `consent_reply` に一本化し、granted/declined は payload のみに置く（差分は列挙2値と分岐1つ）。`consent_state` は質問者ロール射影で無条件に `"n/a"` へ潰す、と §3 に明記する。
    - §3 と §10-14 の文言を「レーン1完結時は回答者の employee_id のみ返す。レーン2に遷移した case では候補20件・配送先k体の employee_id を一切返さない」に統一する。§9 の P0 行「質問者ロール射影」の対象フィールドを `payload` / `intent` / `consent_state` / `from` の4つと明示する。

- [C-13] 種別: 設計 / 深刻度: mid
  - 指摘: **C-6 で導入した資格情報分離が、監査ダッシュボード側では成立しない書き方になっている。** §8-1（＝§3の認証節1）は「監査者ロール用キーは Cloud Run のサーバー側環境変数（Secret Manager経由）に**のみ**保持」と書き、§7 は「クライアントは…Cloud Run サーバーAPI（**監査者専用キー**、§8）経由でポーリング」と書く。監査ダッシュボードがブラウザSPAなら、キーはブラウザに載らざるを得ず両者は排他。さらに §8-2 のセッション認証は「4名の完全実装エージェントに対応する4ユーザーぶん」であり、**監査者という主体がセッション設計に存在しない**。「監査ダッシュボードを開いている人間が監査者であること」を検証する手段が設計書に一行もない。
  - 破綻シナリオ: 実装者が最短経路（監査ダッシュボードもSPA、キーをフロントに埋め込む or `.env` 経由でバンドル）を取ると、監査者キーがブラウザから読める。すると §10-13 の検証（質問者キーで監査エンドポイント→403）は緑のまま通るのに、**監査者キーを拾って全 `decline` を読む経路が開いている**——C-6 の指摘「エンドポイント分離を認可の代替にしない」が、キー配置の未定義によって実質的に元に戻る。Fortified 配点30%「認証情報のセキュリティ」に直撃し、しかも design.md が「フロントに含めない」と明言している分、反証されたときの落差が大きい。
  - 提案: §7/§8 に1文。監査ダッシュボードは **Cloud Run 上のサーバーサイドレンダリング（キーはプロセス内に留まる）** とするか、**セッションに `role: "auditor"` を持つ第5ユーザーを追加**し監査APIはセッションロールで認可する、のいずれかを選んで明記する。後者なら §10-13 の検証も「監査者ロールを持たないセッションで監査エンドポイント→403」に置き換わり、キーの置き場所問題自体が消える（推奨）。

- [C-14] 種別: 設計 / 深刻度: mid
  - 指摘: **C-10 で導入した `MIN_QUOTE_LENGTH=20文字` が、`body` 自体が20字未満の項目からの引用を構造的に不可能にし、正常系のデモ中に `reject_provenance`（赤行）を誤爆させる。** §1手順5 は「`quote` の長さが20文字未満の場合**も拒否**」としか書かず、`body` が短い場合の扱いがない。加えて同手順の逐語引用「最大N文字」の **N が定数化されていない**（`MIN_QUOTE_LENGTH` だけが定数）。
  - 破綻シナリオ: プロフィール項目には「対応可能言語: 英語・中国語」「保有資格: 医療経営士2級」のような短文が自然に混じる。§1手順5 は「空白・改行を正規化した上で比較」するので正規化後は更に短くなる。この項目が最良ヒットになった質問を投げると、送信層は逐語引用を作れず**必ず** `reject_provenance`・`rejected=true` で拒否し、監査ダッシュボードに赤行が出る（§7）。デモ1シーン目（レーン1完結）で赤が出るか、あるいは citation 0件になって C-11 の経路でレーン2へ落ちる。原因が「来歴検証の最小長」だと当日に特定するのは難しく、シードデータ設計（8/19 クリティカルパス）にも遡って影響する。N < 20 の設定ミスでも全件拒否になる。
  - 提案: 判定を `len(normalize(quote)) >= min(MIN_QUOTE_LENGTH, len(normalize(body)))` に変え（body 全体を引く場合は最小長を免除）、§1手順5 に1行で書く。併せて `MAX_QUOTE_LENGTH` を定数として値まで書き、`MAX >= MIN` を不変条件として明記する。§4 のシードデータ規約に「`items[].body` は正規化後40字以上を目安に書く」を足しておくと二重に安全。§10-11 の単体テスト境界値は 19/20 に加え「body が15字の項目からの全文引用」を追加する。

- [C-15] 種別: 設計 / 深刻度: low
  - 指摘: v3 で非同期化したレーン2に、**実行主体と宛先の空白**が3つ残っている。加えて §9/§10 の挿入でセクション内部参照がずれている。
  - 破綻シナリオ:
    1. §5-4「deadline 到達時点で granted が1件以上あれば…成立とし `match_proposal` を発行する」の**評価を誰が走らせるかが未定義**。spec 制約は `min-instances=0` なので常駐タイマーもワーカーもいない。素直に読むと「質問者UIのポーリングリクエストが到達したときに遅延評価」だが、書かれていないため実装者が Cloud Scheduler / Cloud Tasks を足す可能性がある（残工期10日弱に対する過剰実装）。デモでは質問者画面が開いているので遅延評価で十分。
    2. `match_proposal` の**宛先が未定義**（質問者のみ／同意者のみ／両方）。§3 のエンベロープは `to: string` で単一宛先。デモ2シーン目は「同意→15分MTG提案」を映すので、同意した本人の画面に何が出るかが台本上必要（spec FR8）。P2 の「見送り通知は作らない」は明記されたのに、成立側の通知先が抜けている。
    3. §5-2 の「（4体のうちレビュー主体がいる場合のみ）」は、§1手順3 で配送対象が `implemented=true` に限定済みなので常に真。読み手に「配送先に本人不在のケースがある」と誤読させる死んだ条件。
    4. 参照ずれ: §8-1「§9検証ゴールに追加する」→ 実際の検証ゴールは §10。§3「実装優先度はP2。§9直前の優先度表参照」→ 優先度表は §9 そのもの。§1「§11参照」→ 暫定値の記述は §12。§11 の対応表は FR1〜FR16 のみで **FR17（アーキ図・write-up）と完了条件1〜8 の対応行が欠落**（C-11 が見落とされた一因）。
  - 提案: §5 に「deadline 判定は質問者ポーリング到達時にサーバー側で遅延評価する（常駐ワーカーを作らない）」「`match_proposal` は質問者と成立した同意者の双方に発行する」を各1行。§5-2 の括弧書きを削除。§11 の対応表に FR17 行と完了条件1〜8 の列を追加し、参照番号を §9→§10 等で機械的に通し直す。

### その他（指摘には数えない）

- **spec.md 整合性の最終確認**: FR1〜FR17 と完了条件1〜8 を全件突き合わせた。**未充足は完了条件4（＝C-11）のみ**。他は §11 対応表の欠落行（FR17）を除き設計上の対応が存在する。禁止語「承認」は v3 本文に残存なし（完了条件8 の設計段階での充足を確認）。FR11 の逐語フィールド名（`consent` / `audit_id`）と §3 の実装名（`consent_state` / ドキュメントID）の差は実質同一とみなし、指摘に数えない。
- **優先度分類（C-9解決）の妥当性**: round-2 の提案では P1 とした「先着1件成立のバックエンド判定＋`withdrawn` 記録」が v3 で P0 に格上げされている。§9 の P0 基準「デモ一本道に映る、または Fortified 審査軸に直結」に照らすと、n=4 のデモ台本では複数同意は発生しないため P1 が整合的。ただし実装は数行で、P0 に置いても工期を圧迫しないため欠陥としては数えない。表が v2 追加機構のみを対象とし、シード投入・レビューUI・監査UI本体・動画を含まない点も、表の目的が限定的である旨が §9 冒頭に書かれているため許容する。
- **過剰実装の総評**: v3 は v2 から機構をほぼ増やしておらず（追加はセッション認証・優先度表・定数1個）、C-9 の「デモに映らない付随UIを P2 に退避する」判断が効いている。2週間・個人開発に対して**依然として現実的**と評価する。C-11〜C-14 の対処も合計で数十行の範囲に収まる。
- **T_lane1=20秒同期ブロックについて**: C-7 の解決自体は支持する。Cloud Run の既定リクエストタイムアウト（300秒）に対し20秒は安全で、§12 に実測タスクが明記されている。新たな欠陥は見当たらない。
- **embedding の public 限定について**: C-8 の解決自体は支持する。派生の軽微点として (a) 396体の `seed_synth` 項目にも `visibility` が必要（投入時に全 public でよい）、(b) 全項目を private にした社員の embedding が空になる（Firestore ベクトル検索は当該ドキュメントを無視するだけでクラッシュしない）——いずれも実装時に自然に気づく範囲のため指摘に数えない。

### 承認CPへの進行可否

**新規 high 指摘 1件（C-11）があるため、このまま承認CPへ進めることは推奨しない。** ただし C-11 は設計思想の破綻ではなく「デモ3シーン目の発火経路と spec 完了条件4 の因果が設計内に存在しない」という欠落であり、案X/案Yのどちらを採るかをユーザーに1問確認し、§1手順7 に分岐1つと §6 に対応表1つを足せば解消する。C-12〜C-15 は同じ改訂ラウンドでまとめて反映できる規模（合計で設計書10行前後）。**C-11 の1問確認＋v4 の軽微改訂を挟んだうえで承認CPへ進むのが最短。**
