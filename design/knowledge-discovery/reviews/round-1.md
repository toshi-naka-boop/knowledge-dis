- [C-3] 種別: 設計 / 深刻度: high
  - 指摘: 監査ログの**読み取り権限の分離**が設計されていない。§7 は「監査ダッシュボードは神視点、質問者UIとは別物」という**位置づけの宣言**だけで両立を主張しているが、位置づけは実装上の隔離ではない。加えて認証情報の取り扱い（Firestore Security Rules / Cloud Run サービスアカウント / Secret Manager）が design.md に一行もなく、Fortified の配点30%「認証情報のセキュリティ」に対して設計書が無言のままになっている。
  - 破綻シナリオ:
    1. §7 は「`messages` コレクションをリアルタイム購読して表示」と書いている。クライアント SDK で購読する構成にすると、`messages` に read 権限を与えた Security Rules が必要になる。デモ最短経路は `allow read: if true` であり、その瞬間に質問者UIを開いているブラウザからも（DevTools からでも、同じ SDK 経由でも）`consent_state="declined"` の行が読める。「辞退は依頼者に一切表示されない」（spec FR9・完了条件3）は**表示制御でしか担保されておらず、データアクセス制御では担保されていない**。審査員がリポジトリの rules ファイルを開けば1分で反証でき、write-up の中核主張（owner-approved / consent-gated / auditable）が丸ごと信用を失う。
    2. さらに深刻なのはデモ動画そのもの。spec 決定12/FR16 は「レーン1完結→レーン2の同意と不可視辞退→悪性クエリ拒否（監査画面）」を**1シナリオ一本道**と定めている。3シーン目で監査ダッシュボードを全画面で映すとき、その時系列リストには2シーン目で発生した `consent_reply(declined)` 行が `from → to` と `consent_state=declined` 付きで残っている（§7 は各行に from/to/consent_state を表示すると明記）。つまり**「辞退は不可視」を主張する動画が、辞退者の実名と辞退の事実を全世界に公開する**。動画が自らの主張の反例になる。
  - 提案:
    1. クライアントからの Firestore 直接購読をやめ、`messages` は `allow read, write: if false`（サーバー経由のみ）にする。質問者UIも監査ダッシュボードも Cloud Run 上のサーバー API 経由で読み、サーバー側で**ロール別の射影**を行う。質問者ロールへの射影では `consent_reply` の `granted/declined` を落とす。これで「全件記録」と「不可視」がデータ層で両立し、宣言ではなく機構になる。
    2. 監査ダッシュボードの consent 系行の表示ポリシーを決める。推奨は既定表示を `consent_reply received`（結果を伏せる）とし、監査者ロールでのみ展開する二段表示。デモ動画ではこの伏せ表示を映し、「監査は全件記録しているが、辞退の中身は依頼者にも観客にも出ない」とナレーションで言う。この一手で、C-3-2 の自壊が逆に**最も強い訴求ポイント**に反転する。
    3. §8 に、Cloud Run のサービスアカウント権限（Firestore への最小権限）、Gemini API キーの Secret Manager 管理、公開URLの保護方式を1段落で明記する。審査軸に直接対応する項目が設計書に存在しないこと自体が減点要因。

- [C-4] 種別: 設計 / 深刻度: mid
  - 指摘: §5-4 の質問者側状態（「応答待ち」または「マッチなし」）の**遷移条件**が未定義であり、素直に実装するとレイテンシで辞退が漏れる。あわせて、k体のうち複数が同意した場合のマッチ成立ルールも未定義。
  - 破綻シナリオ:
    1. 3体に `consent_ask` を送り、1体が3秒で `declined`、残り2体が無応答だとする。「全員の返信が揃ったら『マッチなし』」だと永久に「応答待ち」のまま。逆に「declined を受け取ったら候補から減算し、残0で『マッチなし』」だと、**辞退が速いほど「マッチなし」が速く出る**。全員が黙っているケース（真の無応答）とは表示までの時間が明確に違うため、質問者は待ち時間の長短から「断られた」ことを推測できる。§5 の但し書き「辞退と単なる無応答を区別させない設計とする」は、時間軸を考慮していないため成立していない。これは n=4 の消去法（D-0-note で write-up 送りに合意済み）とは**別の漏洩経路**であり、こちらはアーキテクチャで安く塞げる。
    2. 3体中2体が同意した場合、§5-3 の記述どおりなら `match_proposal` が2件発行され、質問者に2件のMTGが提案される。spec FR8 は「本人が同意した場合のみマッチが成立」としか書いておらず複数同意を規定していない。デモ台本では1体しか同意しない想定だろうが、実装が未定義のままだとリポジトリを読んだ審査員には状態管理の穴として映る（審査軸「状態管理」）。
  - 提案:
    1. **定時応答（constant-time response）**にする。質問者UIは `consent_ask` 送信時刻から固定T秒（デモなら10秒）経過後に必ず結果を表示し、その間に granted が1件も来なければ「マッチなし」を出す。declined が何件何秒で来ようと表示タイミングは不変。実装は数行で、write-up に「タイミングチャネルまで潰した」と書ける費用対効果の高い一手。同じ待ち合わせ機構を C-1 の `no_match` 集約にも流用できる。
    2. 複数同意時は「先着1件のみ成立、残りの `consent_ask` は `withdrawn` として監査ログに記録し、後着の granted はマッチにしない」を design.md で明文化する（決定5「断るコストゼロ」の思想とも整合する。同意した側に無駄なMTGを発生させない）。

- [C-5] 種別: 設計 / 深刻度: low

  - 破綻シナリオ: 設計書の語彙はそのまま実装の識別子とUIラベルへ伝播する（`approved_docs`、`is_approved`、"Approved knowledge" 等）。8/29 の機能凍結後、write-up 執筆時に完了条件8を満たすため実装・UI・図・動画字幕の全面 grep 置換が必要になり、締切直前に不要なリスクを負う。用語統一は spec 決定15で「思想の一貫性」として位置づけられているため、審査員に見える文言に「approved」が残ると、アンチテーゼとしての立論（owner-reviewed であって approval ではない）が弱まる。
