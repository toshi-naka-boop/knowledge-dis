### 指摘

- [C-31] 種別: 実装 / 深刻度: mid
  - 指摘: **txn 内に移した降格禁止ガードが、resolve 書込み（status open→resolved）まで飲み込む**。ガード分岐は `existing.status=="open" and existing.tier=="request_draft" and card.tier=="notice"` のみで判定し、incoming の `status` / `resolved_reason` を一切適用せずに `outcome="updated"` を返す（`src/knowledge_discovery/store.py:724-735`、`src/knowledge_discovery/firestore_store.py:540-551`）。呼び出し側 `_resolve()` は事前 read の `open_card.tier`（= stale な "notice"）を incoming tier に使うため（`src/knowledge_discovery/secretary.py:829-841`）、この分岐に入りうる。さらに `_resolve` は `outcome in ("created","updated")` で `cards_resolved` を加算するので、**解決していないのに解決 1 件として計上**する。
  - 破綻シナリオ（実測 P1a/P1b/P1c）: 30分 job（run A）が notice カードを事前 read → 07:55/08:00 の別 run（run B）が同カードを request_draft へ昇格 → run A はタスクが `done` なので resolve を書く → ガードが発火して **カードは open / request_draft のまま**（`question_draft`・`preview` も残る）。実測: `task.status=done; after r2: card.status=open tier=request_draft reason=None / summary cards_resolved=1`。ユーザー画面には完了済みタスクの NEED DETECTED カードが残り続け、同 run の Bridge Trace は「解決した」と報告する。次 run では事前 read が request_draft になるため resolve は通る（実測 P1c: q3 で resolved）＝最長 30 分の自己修復だが、その間 `cards_resolved` は延べ 2 回計上される。時間窓は「事前 read → CAS」間（store 往復＝数十 ms）で W-1 本体（LLM 秒オーダ）より狭いが、3系統同時刻構成（07:55 / 08:00 / 毎30分）という前提は W-1 を High と認定したときと同一。
  - 提案: ガード分岐で incoming が open 以外のときは降格禁止を適用しない（`card.status == "open"` を条件に追加）か、ガード分岐内でも `merged.status = card.status` / `resolved_reason` を適用して tier・payload のみ保護する。テストは「open×request_draft に tier=notice の resolved 書込み → status=resolved・tier=request_draft」1 件で足りる。

- [C-32] 種別: 実装 / 深刻度: low
  - 指摘: **C-28 の run_key salt を、reopen が構造的に起こりえない mail→profile_diff の audit id に無条件適用しており、既存の dedup を退行させた**。`msg_diff_` は `sha1(mail_id + ":" + run_key)`（`src/knowledge_discovery/secretary.py:1174-1175`）で、outcome が created/updated/reopened のたびに run ごとの別 id になる。しかし profile_diff カードに `status="resolved"` を書く経路は存在せず（`status="resolved"` の代入は `secretary.py:838` の stagnation `_resolve` のみ）、profile_diff の outcome は created/updated/rejected_* だけ ＝ reopen 用の salt は効果ゼロで、失うものだけが残る。ledger C-28 の指示は「カード副作用 audit の決定的 id に run_key を含める（sha1(card_id:band:run_key)）」＝ 帯付きの stagnation 系 id が対象で、mail 系までは求めていない。
  - 破綻シナリオ（実測 P2）: run A がカード書込みと `profile_diff_proposed` 送出まで進み、`mail.processed=True` を永続化する直前で落ちる（またはメール未処理のまま 07:55 と 08:00 の run が重なる）→ 次 run（別 run_key）が同じメールを再読解し、カードは同一 doc に収束するのに **audit 行だけ 2 行**になる（実測: `after run_A: audit rows=1` → `after run_B: audit rows=2 / cards=1`、ids=`msg_diff_22638f2ec114`,`msg_diff_18d66c8a51bb`）。旧 id（mail_id のみ）なら 1 行に dedup されていた。Bridge Trace に同一メール由来の提案が二重に描画され、Z-4/R4-H4 の「再送＝同 doc」不変条件がこの経路だけ崩れる。
  - 提案: mail 側の audit id を `sha1(mail_id)` に戻す（1 行）。将来 profile_diff に resolved/reopen を導入するなら、そのときに outcome=="reopened" 限定で salt する。

- [C-33] 種別: 実装 / 深刻度: low
  - 指摘: **reopen 時の salt 付き audit と、次 run の salt 無し audit が同一「帯エピソード」に対して二重に出る**。`_send_stagnation_audit` は reopen のみ `card_id:tier:run_key`、通常は `card_id:tier` を使う（`src/knowledge_discovery/secretary.py:773`）。request_draft で作られたカードが resolve され、notice 帯で reopen した場合、reopen run は salt 付き id を書き、**次の run は（未使用の）salt 無し `card_id:notice` id を初めて書く**ため、帯が変わっていないのに 2 行目が出る。
  - 破綻シナリオ（実測 P3）: s1 で request_draft 作成 → s2 で resolve → s3 で notice 帯に reopen（notice 行 1 本） → s4 は同帯・無変化なのに notice 行が 2 本に（ids=`msg_stag_04cb5b36903f`,`msg_stag_3836e7a47bf7`） → s5 以降は 2 本のまま安定。Bridge Trace 上、1 回の再検知が 2 イベントに見える（R4-H2 の「同一帯の再 sweep では何も出さない」抑制がこの境界だけ破れる）。害は監査行 1 本の重複に限られ、カード状態・counts は正しい。
  - 提案: salt 判定を「reopen した run 以降、同帯が続く限り同じ世代 id を使う」形にする（例: reopen 時に `payload["detect_gen"]` を採番し id を `card_id:tier:detect_gen` に統一）。または現状を仕様として §9 に明記し、UI 側で同帯連続行を畳む。

- [C-34] 種別: 実装 / 深刻度: low
  - 指摘: **C-30 の形式検証パターンが末尾改行を通す**。`EMPLOYEE_ID_FORMAT_PATTERN = re.compile(r"^[A-Za-z0-9_-]{1,64}$")` を `.match()` で使っており（`src/knowledge_discovery/server.py:61`, `:408`）、Python の `$` は末尾の改行 1 個の直前にもマッチするため `"marcus_chen\n"` が 400 にならない（実測: `p.match('marcus_chen\n') → True`、`'a/b'` は False）。C-30 で報告された 500（奇数パス要素）は塞がっているので実害は小さいが、E5/C-30 が閉じたと見なした「Firestore doc id に渡る前に弾く」境界には穴が残る。
  - 破綻シナリオ: demo/system principal（human は `_require_self_employee` で自分の id に固定されるため不可）が `PUT /api/secretary/autonomy` に `employee_id="marcus_chen\n"` を送ると、`autonomy_policies/"marcus_chen\n"` という別 doc が 200 で作成される。GET も同じ id で読み戻すのでクライアントには保存されたように見えるが、sweep はレジストリ由来の正しい id を読むため **設定が一切効かない（沈黙する誤設定）**。digest 側は空の digest を返すだけで害はない。
  - 提案: `.fullmatch()` に変えるか、パターンを `\A[A-Za-z0-9_-]{1,64}\Z` にする（1 行）。

### 確認済み（round-6 指摘 5 件の修正が意図どおり効いている点）

1. **W-1（txn 内の降格禁止）**: 降格禁止が `upsert_card_gated` の CAS 内（InMemory は `_card_lock`、Firestore は `@firestore.transactional`）で `existing`（txn 内 read）に対して判定されており、caller の事前 read には依存しない（`store.py:724`, `firestore_store.py:540`）。probe_f 相当の「事前 read が古い」経路を P1b で再現しても request_draft は notice へ落ちず、`question_draft`/`preview` も保持された。`tests/test_autonomy.py:424` に stub による退行テストあり。C-19 の非退行（policy 制限・score 低下での降格なし）も既存テスト 2 件で担保。
2. **W-1/W-3（policy_hold carry-forward）**: `_merge_policy_hold` が「incoming が hold を持つ＝verbatim 勝ち／`clear_policy_hold=True`＝除去／それ以外＝既存 hold を持ち越し」を通常 update と resolved→reopen の両分岐で適用し（`store.py:655-671`,`731`,`741` ／ `firestore_store.py:421-439`,`546`,`557`）、caller 側は事前 read の hold を全経路で `payload.pop("policy_hold")` してから渡す（`secretary.py:864`,`888`,`929`）。W-3 の「reopen で hold が空から作り直されて消える」は解消。
3. **`clear_policy_hold=True` の位置づけとユーザー裁定の整合**: full path（全4許可 ON）だけが True を渡す（`secretary.py:1038-1040`）。scheduled で full path に到達するには eff が全 True である必要があり、eff は policy doc のみから導出され（`_effective_policy`, `secretary.py:373-383`）、hold は eff が全 True でない時にしか書かれない。したがって「hold が存在する かつ hold.policy_updated_at == 現在の policy_token かつ full path 到達」は構造的に成立しない（doc 不在時の既定は search OFF なので token="" 経由の抜け道もない）＝ **hold の除去は必ず policy 変更（token 差）を伴う**。score が T2 を割った run では `score < t2` 分岐が carry-forward で hold を守り（clear は渡さない）、T2 に戻った run で token 一致なら再探索なしにスキップされる（`secretary.py:901-919`）。origin=manual は `policy_token=None` の全許可 override として hold を stale 除去するが、これは round-6 で確認済み・人手起動限定の 1 回で、「毎 run 再探索」には至らない。裁定「設定変更後にのみ再開」と矛盾する経路は見つからなかった。
4. **W-2（Firestore lookup の txn 内化）**: 決定的 id の存在確認（`doc_ref.get(transaction=txn)`）と legacy/domain-key の open 優先 lookup（`txn.get(col.where(...))`）がいずれも `@firestore.transactional` 関数の内側にあり、policy read も含め **全 read が全 write より前**（`firestore_store.py:462-529`）。`google-cloud-firestore 2.28.1` の `Transaction.get` は `DocumentReference | Query` を受理し Query は `query.stream(transaction=self)` に委譲する実装であることをソースで確認したので、実行時 `ValueError` の懸念はない。open 優先・updated_at 降順の選択ロジックは txn 外版（`firestore_store.py:388-419`）と同値。ただし **FirestoreStore の CAS 系は 1 件もテストされていない**（`tests/test_firestore_store.py` の `MockFirestoreClient` に `transaction()` が無く、`upsert_card_gated` を呼ぶテストは InMemory 側のみ）。W-1/W-2/W-3 の Firestore 実装は静的読解のみで確認しており、InMemory 実装との論理差分は今回の読み比べでは検出されなかった（created/guard/reopen/unchanged/rejected_* の全分岐で一致）。
5. **C-28（reopened の counts/audit）と C-30（digest の employee_id）**: reopened は `cards_created` に算入され、`tier=="request_draft"` の reopen は `prev_tier_txn` が request_draft でも `needs_detected` に算入される（`secretary.py:1045-1062`）。salt は stagnation/preview 両方で `reopened` 限定（`secretary.py:773`,`1067`）＝ 通常の同帯再 sweep の抑制は維持（P3 の s5 で追加行なしを確認）、同一 run 内の crash-retry は create-only で dedup（`tests/test_autonomy.py:1143`）。C-30 は `/api/secretary/digest` に `_require_valid_employee_id_format` が入り（`server.py:735`）、`a/b` 由来の 500 は再現しなくなった（残る穴は C-34 の末尾改行のみ）。全 320 テスト green。
