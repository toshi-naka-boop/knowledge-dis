### 指摘

- [C-28] 種別: 実装 / 深刻度: mid
  - 指摘: **一度 request_draft まで昇格したカードが resolve 後に再停滞（outcome=reopened）すると、`needs_detected` も `cards_promoted` も 0 のまま**で、`stagnation_detected` / `preview_search` も再送されない（決定的 audit_id が `sha1(card_id:band)` で band 不変のため dedup）。B群の「昇格判定を戻り値駆動に」の分岐が `prev_tier_txn != "request_draft"` のみで、`outcome == "reopened"`（＝新しい検知イベント）を昇格・検知として数えていない（`secretary.py:1022-1033`、`secretary.py:760`）。
  - 破綻シナリオ（実測 probe_b1、policy 全 ON）: run1 で request_draft 昇格（needs_detected=1、audit 2行）→ タスクが done になり run2 で resolve → タスクが再開して再停滞 → run3 で **同一 doc が reopened し UI には NEED DETECTED が復活する**が、sweep_run の counts は `cards_created=1 / cards_promoted=0 / needs_detected=0`。`audit.html:renderSweepMeta` は `needs===0` で `"no new needs"` を出すため、Bridge Trace は「Automatic sweep — 1 profiles explored · **no new needs**」と表示しつつ My Agent には Need detected カードが出る（design §12-3/§12-4 のスクリーンショット条件と矛盾）。さらに run3 では q_draft 生成＋組織探索＋候補評価（candidates_explored=1）が実際に走っているのに **audit 行が1行も増えない**ため、2回目以降の自律探索が監査系列に残らない（design §3 の「解消履歴は audit の stagnation_detected 系列に残る」という前提が成立していない）。`score_below_t1` resolve → 再停滞でも同様で、30分周期 job では常態的に起きる。
  - 提案: (1) `outcome == "reopened"` かつ `tier == "request_draft"` を `needs_detected`（および昇格系カウンタ）に算入する。(2) 再検知を audit に残すなら audit_id に世代を混ぜる（例 `sha1(card_id:band:card.created/reopen 世代)`）— これは R4-H2 の id 規約の変更なので ledger 記録を伴うこと。(3) §9 にテスト1件（promote→resolve→再停滞で needs_detected=1・新しい stagnation_detected 行）を追加。

- [C-29] 種別: 実装 / 深刻度: mid
  - 指摘: B群は「昇格判定を transaction 内の値で駆動」まで実装したが、**どの書込みを試みるか（tier・payload）の決定は依然 transaction 外の事前 read（`secretary.py:810-811` の `find_card_by_domain_key`）**に依存し、CAS が返す `prev_tier_txn` は書込み後のカウントにしか使われていない。結果、C-19「昇格済み request_draft を降格しない」は**並行 run では成立しない**（`secretary.py:870-882` の降格禁止分岐が古い `open_card.tier` で判定されるため素通りし、`upsert_card_gated` は incoming の tier/payload をそのまま merge する — `store.py:664-668` / `firestore_store.py:494-497`）。
  - 破綻シナリオ（実測 probe_f）: run A（30分 job）と run B（A段 08:00 job／B段 07:55）は run_key が別なので同時に claim・実行できる。両者が同じ notice カードを読み、A が候補ありで request_draft に昇格 → 直後に B の preview 評価が候補0（Gemini 由来 q_draft の run 間ゆらぎ・floor 0.62 近傍で現実的）だと、B の書込みが `tier="notice"` / `preview.candidates=[]` で上書きし、**NEED DETECTED カードが notice に戻る**（実測: `after run A: request_draft` → `after run B: notice, candidates=[]`、outcome は `updated`）。同じ経路で payload 全置換により他 run が書いた `policy_hold` も失われる（C群の保全は単一 run 内でしか効かない）。本番は 07:55 / 08:00 / 毎30分の3系統が同時刻に重なる構成（CLAUDE.md「Deploy/環境」）。
  - 提案: `upsert_card_gated` の戻り値で気付くのでは遅いので、**降格禁止と hold 保全を transaction 内で判定**する（例: incoming に `never_downgrade_from=("request_draft",)` 相当の意図を渡し、txn 内で `prev_tier == "request_draft"` かつ incoming が notice なら書込みを捨てて `outcome="rejected_downgrade"` を返す／payload は key 単位 merge にする）。テストは probe_f 相当の「事前 read が古い」ケースを stub で1件。

- [C-30] 種別: 実装 / 深刻度: low
  - 指摘: E群の `employee_id` 形式検証（E5）が **Autonomy API の2ルートにしか入っていない**。本フェーズで新設した digest 側の実効 policy 読み出し（`secretary.py:1215` `_effective_policy(employee_id)`）は、`server.py:729-735` の `/api/secretary/digest` が受け取った **未検証の employee_id をそのまま Firestore の document id** に渡す（`firestore_store.py:519`）。round-5 S-5 で受理した根本原因が、修正の対象外ルートで再現する。
  - 破綻シナリオ（実測 probe_e5）: demo モード（API キー保持者は任意の employee_id を名乗れる — `_require_self_employee` は human のみ拘束）で `GET /api/secretary/digest?employee_id=a/b` → `collection("autonomy_policies").document("a/b")` はパス要素が奇数となり `ValueError: A document must have an even number of path elements`（google-cloud-firestore の実挙動を実測確認）→ 未処理例外で **500**。`a/b/c` なら 4 要素で有効な入れ子パスの read になる（書込みは発生しないので low）。同 probe で Autonomy API 側は `a/b` `a/b/c` `""` 65文字 いずれも 400 を返し E5 自体は正しく効いている。
  - 提案: `_require_valid_employee_id_format` を digest ルート（および同じ employee_id を store に渡す既存ルート）にも適用するか、`_effective_policy` 側で形式不正を既定 policy にフォールバックさせる。

### 確認済み（修正が意図どおり効いている点 — 反論なしとした観点）

1. **A（単一パイプライン）**: `HEAD` の旧 `run_sweep` を並走させ、同一 fixture（notice/T2/done/低スコア/confirmed/dismissed の6タスク＋未処理メール1件）で5連続 sweep を機械比較。`tasks_evaluated / cards_created / cards_promoted / cards_updated / cards_resolved / diff_cards_created` は**全 run で完全一致**、カード状態（tier/status/resolved_reason/payload）とメール processed/body も run1・run2 で完全一致。差分は設計上の意図的変更のみ: ① 昇格時に `stagnation_detected(request_draft)` が1行増える（R4-H2 の band 別 create-only id）② resolve 後の再停滞で新カードを作らず同一 doc を reopen する（C-13/C-18、旧実装は 8 doc・新実装は 7 doc）。manual は `origin="manual"` の sweep_run audit を毎回 create し、`policy_hold` / `policy_limited` は 0 件（probe_a・probe_c run6）、`get_latest_sweep_run()` も `origin=manual` を返す（C-26 解消）。domain API 既定 origin は "manual" のまま（`gws_probe.py:106` など既存直接呼び出しは無改修で従来挙動）。既存 `tests/test_secretary.py` は**未変更のまま全件 green**（意図反転はこのファイルには入っていない）。`test_autonomy.py` 側の2件（manual の sweep_run 送出＝V-5、rejected_terminal→processed＝K-3）は ledger A/D の裁定と一致する反転で、vacuous ではない。
2. **B（CAS/outcome）**: `outcome="unchanged"` は「既存 resolved × incoming 非 open」でのみ返り、先着の `resolved_reason` を保持（probe_b #4）。domain-key 検索は open 優先＋updated_at 降順で、legacy 乱数 id と決定的 id が混在しても **open カードは常に1枚**（probe_b #2/#3 の両方向で確認 — round-5 K-1/C-23 の再現条件は解消）。カウンタ・stagnation_detected・preview_search はすべて outcome 駆動で、`rejected_*` は無送出・無計上。Firestore 実装は legacy 解決だけ txn 外・read-check-write は `@firestore.transactional` 内（同時 create は同一 doc に収束）。
3. **C（hold 保全）**: prepare OFF で hold 生成 → 不変 run はスキップ → **band が T2 未満へ落ちても hold が残り** → T2 に戻っても再探索も policy_limited も発生せず → `policy_updated_at` を変えた run で初めて再探索＋2件目の policy_limited、という往復を実測（probe_c run1〜run5、shortlist/evaluate 呼び出し回数で確認）。R4-H5・ユーザー裁定「設定変更後にのみ再開」に一致。manual は hold を stale 扱いで除去して全段実行（run6）、その後の scheduled は昇格済みカードを降格しない（run7）。
4. **D（mail matrix）**: terminal（dismissed / applied）な profile_diff カードを持つ未処理メールは **1回目の sweep で processed=True**、以後 LLM 呼び出しゼロ・カードは terminal のまま（probe_d D1/D3、3連 run で `llm_calls=1`）。retention が body を空に落とすことも確認。`rejected_policy_changed` を人工的に発生させた run では **processed=False を維持**（probe_d D2）。誤消費（別メールのカードによる巻き添え）は card_id/domain-key が mail_id 由来のため構造的に起きない。
5. **E（安全性）**: silent-drop は sweep_run / policy_limited の2 intent 限定に戻っており、細工メールで `item_key=""` を返させた scheduled run では **`reject_unregistered_type` の可視行が残る**（probe_e E1。reject 行の payload は payload_type と validator メッセージのみでメール本文を含まない）。`policy_limited` は `from="secretary" / to="system"`、payload は `{stage, run_key, task_count}` のみで、2 owner 分が stage 単位に集約される（probe_e E2: task_count=4、owner 識別子は封筒・payload・audit_view のいずれにも無し）。403/401 は `"invalid token" / "authentication required"` の固定文言のみ（`auth.py:283-297`、期待 audience も失敗段も非開示）、`/internal` の 500 本文は `{"status":"error","run_key":…,"error":"Sweep failed. See server logs for details."}` で例外文・パスなし（`server.py:908-916`、例外は `logger.exception` のみ）。employee_id 形式検証は Autonomy API の GET/PUT 双方で 400（C-30 の対象外ルートを除く）。
